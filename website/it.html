What it takes to run Anchor for your school.

Anchor is self-hosted: your school runs its own backend in your own Azure tenant, and student devices talk only to that. This page is the IT summary — requirements, how it deploys, rollout, the network shape, and running it: the admin pages and what is kept for how long. For the authoritative, step-by-step setup it hands you straight off to the GitHub docs, which are kept current with the code.

Requirements

Anchor is deliberately narrow: Edge-only enforcement on students' Windows laptops, school-managed or their own, and one backend per school. That focus is a design choice, not a roadmap gap — there is no Mac, Chromebook, iPad or phone student client, and no multi-tenant SaaS.

Student agent

Windows 10 version 1809 or later, or Windows 11. A native tray app that installs for one Windows user, needs no admin rights, and starts when they sign in to Windows. How it reaches the laptops is under Rollout below.

Browser

Microsoft Edge (Chromium), with the Anchor extension. Edge-only by design: URL enforcement runs inside Edge, so other browsers are out of scope on the student device.

Teacher dashboard

Any modern browser. The dashboard is a web app — nothing to install on the teacher's side, on whatever device they already use.

Backend

Microsoft Azure, in the school's own subscription: an App Service on the Basic B1 plan (Always On), an Azure SQL Standard S0 database, and the teacher dashboard on a free-tier Static Web App. For a school of around 1,000 students that's about €24 a month (Azure list prices, Belgium Central, excluding VAT), or about €43 if the database needs Standard S1. Azure's free App Service tier can't hold the live connections of a full class, so it isn't an option for real lessons. Single-tenant by design.

How it's deployed

Self-hosted, single-tenant, in your own Azure

You run one Anchor backend for your school, in your school's Azure subscription. The student devices and the teacher dashboard talk only to that backend — your data stays in your Azure.

Sign-in reuses the school's existing Entra ID: teachers and students sign in with the Microsoft accounts they already have, against your own tenant. The deploy creates two single-tenant Entra app registrations (the API and the dashboard SPA); there are no separate Anchor passwords to manage and no third-party identity provider in the loop.

Rollout

Three pieces, in this order: the backend, the agent, then the extension. The GitHub docs carry the exact commands and settings — this is the shape of the work.

01

The backend

In your school's fork of the repository, stand up your Azure backend with scripts/setup.ps1 — one command provisions the resources, the Entra registrations, and the GitHub deploy wiring. A direct Bicep deploy and a portal walkthrough are documented as manual alternatives.

02

The agent

Push an agent release tag on your repository. The release workflow builds a Setup.exe with your backend's address and Entra IDs baked in and publishes it on your repository's GitHub Releases, together with an install script for Intune. On school-managed laptops, package the two as an Intune Win32 app that installs for the signed-in student and starts the agent right away; the Intune guide has the settings. After that the agent updates itself. A new release needs Intune only when you raise the detection rule's minimum version, to reach laptops whose agent hasn't updated itself; the Intune guide explains when. On their own laptop, a student runs the Setup.exe themselves: no admin rights needed, though the installer isn't code-signed yet, so Windows SmartScreen asks them to confirm once.

03

The extension

On school-managed laptops, an Intune configuration profile force-installs the Anchor extension from the Edge Add-ons store; the agent finds that policy and asks the student nothing. On other laptops the agent offers to set the same Edge policy itself, with one Windows permission (UAC) prompt. If the student can't or won't approve it, the agent opens the store listing so they can add the extension in one click. Uninstalling the agent offers to remove the policy it set (another UAC prompt) and never touches one your Intune profile manages.

Network

Plain HTTPS outbound — no proxy surgery

Everything runs over HTTPS/TLS. Each student device makes outbound connections to your school's App Service (by default anchor-api-<suffix>.azurewebsites.net), which serves both the API and the realtime session channel. The realtime channel runs inside the API itself, so there is no separate SignalR service to allow — just make sure outbound HTTPS to that host permits WebSocket upgrades. Beyond that, devices sign in through Microsoft Entra ID (login.microsoftonline.com), and the agent checks your repository's GitHub Releases for updates.

Anchor needs no proxy certificate, no TLS interception, and no MITM on its connections. Because enforcement and reporting are device-resident and outbound-only, it is BYOD-friendly: it does not depend on devices sitting behind a particular network, so it works on whatever network the laptop is on.

Running it

Once the backend runs, the school is set up from the dashboard itself. Its admins see one more tab there, Admin, which holds the pages below.

Admins

Admin isn't an Entra role: Anchor keeps it in its own database. You promote the first admin once, with scripts/promote-admin.ps1, as the setup guide describes. After that, admins promote others under Admin → Admins, from the people who have signed in to the dashboard at least once. The last admin can't be removed.

Bundles

The catalogue teachers pick from when they start a session: each bundle is a named set of websites and apps. Only admins create, edit, archive, import and export bundles; an edit applies from the next session that starts. A bundle a session has used can be archived, not deleted.

Schools and lesson periods

Schools come from your directory: each companyName on your Entra ID users is a school, active until an admin switches it off, and teachers see only the active ones. For each school an admin enters its lesson periods, one timetable for every school day; its teachers can then end a session at the end of this or the next period.

School directory

Teachers fill their classes from Entra ID: they search students by name, import a CSV of their sign-in names, or add every user whose companyName is the class's school and whose department is its class code. Keep those two attributes filled in. The backend reads the directory through Microsoft Graph, on behalf of the teacher, with the User.Read.All permission the setup consents to.

Agent logs

Diagnostic log uploads are off until you set the App Service setting LogUpload__Enabled to true; tell students and parents before you do. Each agent then uploads its log lines from around each session its student was on the class list of, and nothing else. Only admins can download them, under Admin → Logs, giving a purpose and a reason; every download is recorded, and the access history exports as CSV for the school's leadership or data protection officer. The privacy policy says what the logs hold and what they may be used for.

Retention

Where the retention periods are set

How long the backend keeps data is set in its App Service application settings: EventRetention__RawEventDays (default 14) for a session's events, LogUpload__RetentionDays (14) for diagnostic logs, and LogAccess__RetentionDays (365) for the records of their downloads. docs/RELEASE.md lists every setting.

No setting covers the rest. Per-student summaries and the sessions themselves, with who took part, are kept until a teacher deletes their class together with its sessions, and Anchor deletes no account by itself. The privacy policy lists what each kind of data holds.
